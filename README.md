# deal-room — Milestone 4

A CrewAI pipeline that turns unstructured pitch text into a decision-ready
investment memo. Since Milestone 3, there's no fixed pipeline order at all:
a Managing Partner agent acts as the crew's **manager**, deciding at runtime
which of its 4 specialists (financial, market, technical, risk) to consult,
in what order, and whether to follow up — all running on Cerebras via
LiteLLM. Milestone 4 adds persistent memory (recall across separate
`kickoff()` calls) and two custom tools (live web search, PDF pitch-deck
reading) — see ["Milestone 4: memory and custom
tools"](#milestone-4-memory-and-custom-tools) below.

> **Correction:** An earlier version of this section claimed vague-financials
> inputs cost more tokens than normal inputs (848K vs ~400K). This was measured
> using a shared LLM instance across sequential kickoffs and reflects a
> cumulative running total, not per-run usage — the underlying bug (and its
> fix: a fresh, unshared `LLM` instance per agent per run) is documented in
> ["Known measurement limitations, and the fix"](#known-measurement-limitations-and-the-fix)
> below. **This claim is retracted.** See the re-run batch results in that
> same section for corrected, per-run token figures.

## What this milestone demonstrates

- **`Process.hierarchical` and dynamic delegation (this milestone's main
  point)**: in Milestone 2, the Managing Partner ran a normal task at a
  fixed position in a fixed sequence, synthesizing four pre-computed
  outputs handed to it via `context`. In this milestone it's structurally
  different: it's passed to the `Crew` as `manager_agent=`, not included
  in the `agents` list, and there is exactly one `Task` —
  `produce_investment_memo` — with **no `agent` set at all**, in
  `tasks.yaml` or in `crew.py`:

  ```python
  return Task(
      config=self.tasks_config["produce_investment_memo"],
      output_pydantic=InvestmentMemo,
  )
  ```

  That absence of a fixed `agent` is what makes this hierarchical: CrewAI
  grants a task's executing manager a "delegate work to coworker" / "ask
  question to coworker" tool pair scoped to every agent in the crew only
  when the task has no fixed `agent` (`crew.py`'s `_update_manager_tools` —
  if `task.agent` is set, the manager only gets a delegation tool scoped
  to that one agent, which is effectively a no-op). With no fixed agent,
  the Managing Partner decides, live, which specialists to call, how many
  times, and what exactly to ask each one. **None of that sequencing is
  encoded anywhere in this codebase** — it's an LLM decision made fresh on
  every `kickoff()`.

  This is the core CrewAI hierarchical pattern with **no clean LangGraph
  equivalent**. A LangGraph graph's topology — which node can run next —
  is fixed at graph-build time, even for conditional edges: the *set* of
  possible next steps is author-defined, and the graph picks among them.
  Here, the sequence and repetition of specialist calls isn't chosen from
  a pre-declared set of edges at all; it's generated by the manager
  agent's own reasoning, task by task, and could in principle be different
  on every run against the same input.

  A structural gotcha worth flagging: the Managing Partner **cannot** be
  both the manager and a regular crew member. CrewAI's own validator
  rejects a crew where `manager_agent` also appears in `agents`
  (`manager_agent_in_agents`) — and CrewAI's `@agent` decorator
  auto-registers every decorated method into `self.agents` regardless of
  whether any task references it. So `managing_partner()` in `crew.py` is
  a plain method, deliberately **not** decorated with `@agent`, called
  only once, directly, when building the `Crew`. LangGraph has no
  equivalent concern — it has no structural distinction between a
  "manager node" and a "worker node" in the first place.

- **The `agents.yaml` / `tasks.yaml` config pattern** and **structured
  output via `output_pydantic`**: unchanged in spirit from Milestone 2 —
  see that section below for the mechanics. One addition: CrewAI eagerly
  resolves every `output_pydantic:` / `agent:` string found *anywhere* in
  `tasks.yaml` at crew-construction time, regardless of whether a live
  `Task` object is ever built from that entry. Milestone 2's 4 analyst
  task definitions (`analyze_financials`, `analyze_market`,
  `analyze_technical`, `assess_risk`) are still in `tasks.yaml` as
  historical reference — but they're never turned into `Task` objects in
  `crew.py` anymore. Their `output_pydantic` and `agent` registrations
  (the `output_pydantic(FinancialAssessment)` class attributes and the
  4 `@agent` methods) still have to exist regardless, or crew construction
  `KeyError`s trying to resolve those unused YAML entries.

- **Cerebras as a non-native LiteLLM provider**: CrewAI has a handful of
  natively-wrapped providers (OpenAI, Anthropic, Gemini, Azure, Bedrock).
  Cerebras isn't one of them, so it's routed through LiteLLM using the
  `cerebras/<model>` string prefix. `crew.py` builds the `LLM` object
  explicitly (via `DealRoomCrew._new_llm()`, called once per agent — see
  "Known measurement limitations, and the fix" below for why it's one
  call per agent rather than one shared object) and passes it to each
  agent instead of relying on env-var inference, which is important — see
  Troubleshooting below.

## Milestone 2 recap: task output chaining via `context`

Milestone 2's `write_memo` task (now removed) never received
`{company_info}` at all — its only input was the structured output of the
four analyst tasks, wired explicitly via `context=[self.analyze_financials(),
...]`. This is CrewAI's equivalent of LangGraph's explicit shared-state
object, but the mechanism differs: LangGraph passes a single mutable state
object through the graph, while CrewAI threads *prior Task objects*
through `context` — each upstream `Task`'s `TaskOutput` gets serialized
into the downstream task's prompt, resolved once at crew-construction time
via memoized `@task` methods.

The gotcha that milestone surfaced: CrewAI's default for an *unset*
`context` in `Process.sequential` is not "no context" — it's
"auto-aggregate every prior task's output so far." The four analyst tasks
needed `context=[]` explicitly to run independently; without it,
`analyze_market` silently inherited `analyze_financials`'s findings.
LangGraph has no equivalent implicit-leak failure mode, since state access
there is always explicit per node.

## Milestone 2 vs Milestone 3

| | **M2 — sequential** | **M3 — hierarchical** |
|---|---|---|
| Process | `Process.sequential` | `Process.hierarchical` |
| Who calls each specialist | Fixed: the crew calls each analyst task directly, in declared order | Dynamic: the Managing Partner (manager) decides, via delegation tools |
| Order of specialist calls | Fixed at code-write time (financial → market → technical → risk → memo) | Decided by the manager at runtime; not guaranteed to repeat run to run |
| Coverage of the 4 specialists | Guaranteed — all 4 tasks always execute | **Not guaranteed in principle** — 3 of 4 cleanly-logged single runs consulted all 4 specialists; 1 consulted only 2 and fabricated the rest itself (see below). A later parallel batch couldn't re-check this at first (logging bug), but the fixed re-run batch (see ["Known measurement limitations, and the fix"](#known-measurement-limitations-and-the-fix)) showed all 4 specialists consulted in all 4 runs, including the one that crashed — so the earlier skip is a real possible outcome, just not what happened in the runs measured since |
| Re-querying a thin answer | Not possible — each task runs exactly once | **Negative result, well-supported**: never observed as a genuine quality-driven re-query across every cleanly-logged run to date, including a pitch with financials deliberately stripped out to invite one. See "Re-query behavior" below |
| `output_pydantic` reliability | 100% (2/2 runs) — one fixed final task, same prompt shape every time | Mixed, and it changed shape after adding `Literal` constraints (see below) — roughly half of all runs to date parsed cleanly, for two *different* reasons pre- and post-`Literal` |
| Determinism | High — same 5 tasks, same order, every run | Lower — delegation coverage, call count, and (as far as we could reliably measure) cost varied run to run on identical input |
| Cost (normal pitch, single clean run) | 60,580 tokens / 25 requests / 63.6s | **94,920 tokens / 15 requests / 444.4s** (fresh, unshared `LLM` instance per agent — see the fix below). Supersedes the earlier "~390,000–410,000 tokens" figure, which turned out to be inflated by the *same* bug as the vague-pitch retraction below, not just a genuinely bigger run — **~1.6x tokens, fewer requests, ~7x time** vs. M2 |
| Cost (vague-financials pitch) | not tested | **79,326 tokens / 14 requests / 437.6s**, measured cleanly after the fix below (one run — not a robust comparison, just no longer a contaminated one). An earlier version of this README claimed vague-financials cost *more* than the normal pitch (848K vs ~400K tokens); that comparison is **retracted** — see ["Known measurement limitations, and the fix"](#known-measurement-limitations-and-the-fix) below. This one clean pair of runs shows vague costing slightly *less*, not more, but treat that as directional given n=1 per case |
| When you'd choose it in production | You know the analysis steps in advance and want predictable cost/latency and easy debugging — a fixed checklist, not a judgment call | The set of needed steps genuinely varies by input in a way you can't enumerate in advance, and you can tolerate occasional parsing failures / incomplete specialist coverage as a cost of that flexibility |

The determinism-vs-flexibility tradeoff is still the real headline, but
testing this milestone twice (once as a small anecdotal single-run set,
once as a small parallel batch) taught us as much about **how hard this
system is to measure correctly** as about the system itself. What's
solid: M3 costs several times more tokens/requests/time than M2 for a
successful normal-pitch run, and its `output_pydantic` reliability is
real, not a superstition — see the two distinct failure modes below. What
turned out not to be solid: the "vague costs more" claim, which came from
a token-accounting bug in how we tested it, not from the hierarchical
process itself. If you need "always run these 4 checks, every time, and
get a parseable result," M2's explicit sequence is both cheaper and
structurally guaranteed. Hierarchical delegation buys adaptability, at a
real and now better-understood cost in reliability — but be skeptical of
any cost *comparison* across inputs unless you've confirmed the
measurement isn't contaminated the way ours was.

## Milestone 3 verification findings (initial testing, 4 cleanly-logged single runs)

Four sequential, individually-run `kickoff()` calls against identical
code — each its own Python process or first-in-process, so none of the
token-accounting contamination described later applied to these:

**1. Does the manager delegate to all 4 specialists, or skip any it judges
unnecessary?** Both happen. 3 of 4 runs delegated to all 4 (financial,
market, technical, risk), each contacted exactly once. 1 run stopped after
2 (financial, market) and wrote the technical and risk sections itself —
and that run is also the one that crashed on `output_pydantic` parsing
(see finding 4). Coverage of all 4 specialists is an emergent outcome of
how the task is phrased, not a guarantee.

**2. Cost vs. M2's 60,580 tokens / 25 requests / 63.6s.** The two
successful normal-pitch hierarchical runs came in at 391,855 and 405,385
tokens (50 and 65 requests; 260.4s and 377.6s) — call it **~6.5x the
tokens, ~2.3x the requests, ~5x the wall-clock time** of M2's fixed
sequence, for the same input. (An earlier version of this section also
claimed the vague-financials pitch cost more than the normal one — that
claim has been retracted; see "Known measurement limitations" below.)

**3. Does `output_pydantic` still parse the manager's final output
correctly?** 3 of 4 times, yes, cleanly. The 4th time it raised a real
`pydantic_core.ValidationError` — 5 fields failed, all because the
manager returned nested dicts/objects (e.g. `{'current_mrr_usd': 42000,
...}`) for fields the `InvestmentMemo` model declares as `str`
(`financial_summary`, `market_summary`, etc.). This happened in the same
run that only consulted 2 of 4 specialists — plausibly, the manager wrote
richer structured content itself for the sections it didn't delegate,
and that structure leaked into fields meant to hold prose. A softer,
non-fatal version of the same fidelity issue showed up in a run that did
parse: `confidence` came back as `"moderate"` rather than one of the
`"high"`/`"medium"`/`"low"` values every other task in this codebase
uses — harmless at the time only because `confidence` was typed as a bare
`str` with no `Literal` constraint. **This has since been fixed** — see
"Adding `Literal` constraints" below for what changed and what it revealed.

Full logs: `/tmp/m3_run.log` (normal pitch), `/tmp/m3_vague_run.log`
(vague-financials pitch).

## Re-query behavior: negative result

Across every cleanly-logged run tested for this — the two runs above plus
the first run of an earlier, since-superseded sequential batch attempt —
**the manager never re-queried a specialist for a thin or hedged answer,
despite `produce_investment_memo`'s task description explicitly
instructing it to do so** ("if any specialist's initial answer is too
thin or vague, re-query them for more detail before finalizing"). This
was tested deliberately: one pitch had burn rate, runway, CAC, LTV, and
funding amount stripped out specifically to produce a thin financial
answer. The financial analyst responded with an appropriately hedged
"insufficient data" assessment, and the manager accepted it as final
without a follow-up question, every time.

The only repeat delegation calls observed anywhere were mechanical:
`Error executing tool. coworker mentioned not found` — the manager's tool
call didn't format the `coworker` argument in a way CrewAI's fuzzy
matcher accepted, so it retried the identical question moments later.
This happened a handful of times, always targeting the "Technical Due
Diligence Lead" role specifically, and always resolved on the next
attempt. That's a tool-call formatting hiccup, not the "notice a thin
answer and dig further" behavior the prompt asked for.

We're stating this as a finding about how this version of CrewAI's
hierarchical process actually behaves, not as a bug to fix. It's possible
a different phrasing of the task description, a different underlying
model, or a future CrewAI version would trigger the behavior — but as
built and tested here, instructing the manager to re-query on request
did not produce that behavior even once, including under an input
designed specifically to invite it. We have not attempted to force this
by rewriting the manager's prompt; the value of this milestone is in
observing the actual behavior, not engineering the test until it shows
what we expected going in.

## Adding `Literal` constraints

`confidence`, `moat_credibility`, `overall_risk_level`, and
`recommendation` were changed from bare `str` to `Literal[...]` types in
`models.py`, to stop the kind of silent drift described in finding 3
above (`"moderate"` sneaking past a field meant to only ever be
`"high"`/`"medium"`/`"low"`). This worked exactly as intended, and
immediately proved its worth: in the very next batch of testing, a run
failed pydantic validation because the manager returned
`recommendation="needs_more_diligence"` (underscored) instead of
`"needs more diligence"` (the exact literal value declared). Before this
fix, that value would have silently passed as a valid string; after it,
pydantic correctly rejected it.

This is a genuine tradeoff, not a pure improvement: `Literal` constraints
turn *silent semantic drift* into a *loud validation failure*. That's
usually what you want in a system whose output feeds decisions
downstream — but it means adding `Literal` types can make a pipeline's
measured parse-success rate look *worse*, not better, if the model's
exact-string adherence is imperfect. The fix didn't make the manager more
reliable at hitting exact literal values; it made the pipeline more
honest about when it doesn't.

## Small parallel batch (n=4): first attempt (superseded)

A planned n=20 sequential batch (10 normal + 10 vague-financials) was
scoped back to a small n=4 parallel batch (2 + 2, run concurrently via
`ThreadPoolExecutor`) for time — sequential n=20 was estimated at 2-3
hours; this trades sample size for a result in roughly one run's worth of
wall-clock time. **Treat everything in this section as directional, not
statistically robust — n=4 barely supports a trend, let alone a rate.**

**Results**: 2 of 4 runs succeeded (both vague-financials: `pass`/`low`
and `needs more diligence`/`medium`); 2 of 4 failed (both normal-pitch —
one hit a real Cerebras rate limit from the concurrent load, one hit the
`Literal`-driven validation failure described above). Total batch
wall-clock was 912.7s for all 4 runs together, against 423.9s and 853.2s
for the two that completed — some parallelization benefit is visible,
but concurrent rate-limit contention measurably slowed individual runs
down (853.2s is far longer than any single vague-pitch run timed
previously), eating into the benefit.

**This batch also surfaced two real problems with the test harness
itself, not with the crew:**

1. **Concurrent kickoffs against a shared Cerebras API key trigger real
   rate limiting.** Running 4 crews at once produced `429` errors on both
   requests-per-minute and tokens-per-minute limits. CrewAI retried some
   of these automatically (visible as `recover_from_context_length`
   listener activity), but one run exhausted its retries and failed
   outright. Parallelizing hierarchical crews isn't free even before
   counting reliability — it can push you over your own rate limit. (This
   is unrelated to the two bugs below and is not fixed by them — it's a
   real capacity constraint of the shared Cerebras key.)

2. **Per-run token/request figures were unreliable whenever more than one
   `kickoff()` shared a Python process with another, sequential *or*
   concurrent.** `crew.py`'s `cerebras_llm` was one shared `LLM` instance,
   and CrewAI's own usage tracking is explicit about this in
   `base_llm.py`: `get_token_usage_summary()` returns *cumulative
   lifetime totals for that LLM instance*, not a per-`kickoff()` delta.
   Two runs in this batch reported the *exact same* total (983,580
   tokens / 245 requests) despite being different input types running at
   different times — strong direct evidence the counter was being read
   at overlapping points by concurrent threads rather than reflecting
   each run's own isolated usage. A separate bug in the batch script
   itself compounded this: per-run verbose-log capture (used to count
   which specialists were consulted) also failed under concurrent
   execution — CrewAI's internal rendering doesn't appear to run on the
   same OS thread that called `kickoff()`, which broke a
   `threading.local()`-based log redirection scheme. Both successful runs
   in this batch produced fully valid `InvestmentMemo` objects (proving
   real delegation work happened), but with almost-empty per-run logs, so
   `specialists_consulted` read as 0 for every row in
   `/tmp/m3_batch_results.csv` regardless of outcome — that column was not
   usable from this batch.

**Skip-correlates-with-crash hypothesis**: not testable from this batch —
not "replicated" and not "not replicated." The `specialists_consulted`
column was uniformly 0 due to the logging bug above, so it carried no
discriminating signal for either failure in this run. Both bugs above are
now fixed — see the next section for how, and for the re-run results.

Per-run CSV (first attempt): `/tmp/m3_batch_results.csv`. Per-run logs
(where non-empty): `/tmp/m3_batch_run_*.log`.

## Known measurement limitations, and the fix

The first batch's two harness bugs above turned out to share a root
cause broader than "one `kickoff()` sharing state with another": **every
agent in a single hierarchical run — all 4 specialists plus the
manager — shared the exact same `cerebras_llm` object**, not just across
separate kickoffs. That matters because of two separate CrewAI behaviors:

1. `LLM.get_token_usage_summary()` accumulates on the LLM *instance*,
   for its entire lifetime — not scoped to a single `kickoff()`. A
   module-level `cerebras_llm` shared across every `kickoff()` in the
   process made token/cost figures a running total across *runs*.
2. `Crew.calculate_usage_metrics()` sums `agent.llm.get_token_usage_summary()`
   over *every agent in the crew*. If several agents share one LLM
   instance, that same cumulative number gets added into the crew-wide
   total once per agent sharing it — 5 agents (4 specialists + manager)
   sharing one LLM instance meant every single-run total reported here
   was **inflated roughly 5x**, independent of the cross-run contamination
   in (1).

This means the earlier "~390,000–410,000 tokens" per-run figure quoted
above for a normal-pitch run — previously described as "uncontaminated"
because it was the first kickoff in its process — was **also inflated**,
just by bug (2) instead of bug (1). It wasn't a fair per-run number
either. Both bugs share the same fix: **never let two agents, or two
runs, share one `LLM` instance.** `crew.py` now builds a fresh,
unshared `LLM` object per agent per `DealRoomCrew()` instance
(`DealRoomCrew._new_llm()`), so nothing survives across kickoffs and
nothing gets summed more than once within a kickoff.

The specialist-tracking bug also needed a different mechanism, not just
a fix to the old one: `threading.local()`-based `sys.stdout` redirection
inherently can't work here, because CrewAI's verbose rendering doesn't
run on the calling thread. The replacement uses CrewAI's own
`AgentExecutionCompletedEvent` on its global `crewai_event_bus` — a
callback-style hook (see `crewai.agent.core.Agent._finalize_task_execution`)
that fires once per completed `execute_task()` call regardless of
internal tool-calling path, with the actual `Agent` instance attached. A
run-scoped registry in `crew.py` (`SpecialistCallLog`, keyed by a
per-`DealRoomCrew` `run_id`) attributes each completion to the run it
belongs to, so concurrent kickoffs no longer cross-contaminate each
other's counts. (An initial attempt used Agent-level `step_callback`
instead, per CrewAI's documented step/task callback mechanism — but that
turned out to never fire for these specialists at all: CrewAI's
`AgentExecutor` has a fast path for zero-tool agents that skips the step
callback entirely, and every specialist here has no tools. Verified
directly before switching approaches.)

## Milestone 4: memory and custom tools

Milestone 4 adds two things to the M3 hierarchical crew: CrewAI's unified
`Memory` (recall across separate `kickoff()` calls, not just within one),
and two custom `BaseTool` subclasses (`tools.py`) — live web search and PDF
pitch-deck reading — attached to the specialists. Both are always on now;
there's no separate "M4 mode."

**Read this section's status up front**: Part B (tools) is fully verified
with real, live evidence. Part A (memory) is verified as a mechanism in
isolation, but the specific two-kickoff recall test never completed live —
blocked by a real Cerebras API quota exhaustion, not a defect found in the
design. Part C's dedicated verification script was written and its pieces
smoke-tested, but wasn't run end-to-end for the same reason. Details below,
reported honestly rather than assumed.

### Part A: memory

`crew.py`'s `_new_memory()` builds a `crewai.memory.unified_memory.Memory`
instance with:

- `embedder={"provider": "onnx"}` — chromadb's bundled `all-MiniLM-L6-v2`
  ONNX model, downloaded once (~80MB, cached under `~/.cache/chroma/`) and
  run entirely on-device. **This was a deliberate, necessary override, not
  a default**: `Memory`'s own `_default_embedder()` builds an
  `OpenAIEmbeddingFunction` (`text-embedding-3-small`) when `embedder` is
  left unset, and separately, `ChromaDBConfig`'s default embedding function
  docstring claims "using all-MiniLM-L6-v2 via ONNX" while the code right
  below it actually builds `OpenAIEmbeddingFunction` regardless — a
  docstring/code mismatch in CrewAI itself. Leaving `embedder` unset here
  would have silently required `OPENAI_API_KEY`, exactly what this task
  asked to avoid or flag.
- `llm=` a dedicated, fresh Cerebras `LLM` instance (via `self._new_llm()`,
  never shared with any agent) for Memory's own internal encode/recall
  analysis — instead of the class default `llm="gpt-5.4-mini"`, also
  OpenAI-shaped.
- `storage=LanceDBStorage(path=<project-root>/.crewai_memory)` — a fixed,
  project-local, file-based path (gitignored), so memories saved in one
  `DealRoomCrew()` instance's kickoff are recallable by a *different*
  instance's kickoff later, which is what the recall test below depends on.

**Mechanism verified directly, in isolation** (cheap, no full crew run
needed): constructing two separate `Memory()` Python objects pointed at the
same storage path, calling `.remember()` on the first and `.recall()` on
the second, correctly stored and retrieved a fact about "Brightledger" with
LLM-inferred entities/categories/importance, using only Cerebras + the
local ONNX embedder — zero OpenAI calls involved:

```
remembered record: id='345aa0c4-...' content='Brightledger is a B2B SaaS
company with a risk profile of medium...' categories=['B2B', 'SaaS', 'Risk
Profile', 'Regulatory Exposure'] metadata={'entities': ['Brightledger'], ...}
recall results: [MemoryMatch(record=MemoryRecord(...same content...),
score=0.71, match_reasons=['semantic', 'recency', 'importance'])]
```

CrewAI also turned out to auto-save and auto-recall without any explicit
tool call needed: every agent's `execute_task()` — including specialists
reached via ad-hoc delegation, not just crew-dispatched tasks — calls
`_save_to_memory()` on finishing (extracts and remembers facts from its own
answer) and `_retrieve_memory_context()` before answering (recalls
relevant memories and injects them into its own prompt), as long as
`agent.crew._memory` is set. No prompt changes were needed to make this
happen; it's automatic, not tool-gated, in this CrewAI version.

**The live, full end-to-end test (Part A's actual ask): not completed.**
`main.py` runs kickoff #1 (Brightledger, full `company_info`) then kickoff
#2 (a follow-up question naming Brightledger but not re-supplying any
figures) in the same process, checking whether kickoff #2's own output
reproduces kickoff #1's specific numbers. Kickoff #1 succeeded cleanly (see
cost table below). Kickoff #2 failed twice, both times before producing a
usable answer:

1. First attempt: a Cerebras `429` ("Tokens per minute limit exceeded")
   during CrewAI's own `recover_from_context_length` repair path — which
   itself makes an LLM call to summarize messages — with no further
   fallback, propagating as an unhandled exception.
2. After adding retry-with-cooldown logic (`kickoff_with_retry()` /
   `RATE_LIMIT_COOLDOWN_SECONDS` in `crew.py`) and re-running from a clean
   memory store: a Cerebras `429` again, but this time "Tokens **per
   day** limit exceeded" — a daily quota, not a transient per-minute one, so
   no cooldown fixes it. Swapping in a second, different-looking
   `CEREBRAS_API_KEY` and retrying immediately hit the *identical* error on
   the very first LLM call of the run — strong evidence the daily quota is
   shared at the Cerebras **account** level, not per-key, so the swap
   didn't add fresh headroom.

This is a real, external capacity constraint, not something the memory
integration code is doing wrong — but it means the specific claim "kickoff
#2 recalls kickoff #1's facts, verified end-to-end" **cannot be reported as
confirmed**, only as architecturally sound and ready to verify once quota
allows. `main.py` is left with the retry/cooldown logic and the full
two-kickoff + recall-marker-check flow in place; re-running
`PYTHONPATH=src python -m deal_room.main` once the account's daily quota
resets will produce the actual recall verdict.

One relevant data point from the run that did succeed: **memory adds
substantial LLM load of its own.** Kickoff #1's crew made 22 requests
(111,197 tokens); Memory's own dedicated analysis LLM — save-extraction
and deep-recall query distillation, one call per agent step of either kind
— made **75 separate requests (122,362 tokens)**, more request volume than
the entire hierarchical crew's own work. That's very likely what pushed
this run into the rate-limit contention described above; enabling memory
roughly doubles total token spend and adds several times the request count
of the underlying crew.

### Part B: custom tools

`tools.py` adds two `BaseTool` subclasses:

- **`WebSearchTool`** (assigned to `market_analyst`): wraps crewai-tools'
  `SerperDevTool` when `SERPER_API_KEY` is set, falling back automatically
  to `ddgs` (a keyless DuckDuckGo wrapper) when Serper isn't usable.
  Verified directly: the `SERPER_API_KEY` present in `.env` returns `403
  Forbidden` — an unauthorized/placeholder value, consistent with this
  README's earlier note that Serper "isn't used yet." A hand-rolled
  `requests` + HTML-scrape fallback was tried first and rejected: DuckDuckGo's
  plain HTML endpoint intermittently returned a bot-detection challenge
  page instead of results, even moments after a successful call — too
  unreliable for a tool whose invocation this milestone needs to actually
  confirm. `ddgs` returned real results reliably in every test.
- **`PitchDeckReaderTool`** (assigned to all 4 specialists): extracts text
  from a PDF via PyMuPDF. `generate_sample_pitch_deck.py` programmatically
  builds a fictional 5-page Brightledger deck
  (`src/deal_room/sample_data/brightledger_pitch_deck.pdf`) with detail
  `company_info` deliberately never mentions — named competitors (Tipalti,
  Bill.com), the actual tech stack (AWS/Kubernetes/FastAPI/Postgres+Redis,
  SOC 2 Type I in progress), and funding terms ($2.5M seed at a $12M
  pre-money cap) — so a specialist has a genuine informational reason to
  read it, not just a tool available to call for its own sake.

**Live invocation confirmed, with real counts**, from the successful
kickoff #1 run's verbose trace: `read_pitch_deck` was invoked **16
times** and `web_search` **34 times** across the specialists. More
tellingly, deck-only facts showed up verbatim in the *final* memo —
`Tipalti`, `Bill.com`, `Kubernetes`, `FastAPI`, `SOC 2 Type I`, the "$2.5M
seed at a $12M pre-money" figure, and "both co-founders are first-time
founders" all appear in the market/technical/risk sections of the output —
proof the tool's content was actually synthesized into the memo, not
fetched and ignored. Neither tool needed the manager to be told a deck
existed in the task input text; each tool's own `description` (shown to
its agent regardless of what the manager asks) was enough for specialists
to discover and use it autonomously.

`verify_m4_integration.py` was written to confirm this same thing more
rigorously — via CrewAI's `ToolUsageFinishedEvent` on the global event bus
(the same "hooks, not log-scraping" principle as M3's Fix 3, rather than
grepping the verbose trace by hand) — but wasn't run live itself; see
"What blocked full verification" below. The manual log-count evidence
above is real and from an actual live run, just gathered differently than
that script does it.

## Running it

1. **Python version**: this project targets Python 3.11.

2. **Create a venv and install dependencies**:

   ```bash
   cd deal_room
   python3.11 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   ```

3. **Set up your `.env`**:

   ```bash
   cp .env.example .env
   ```

   Then edit `.env` and set:

   ```
   CEREBRAS_API_KEY=your-key-here
   ```

   Get a key from the [Cerebras Cloud dashboard](https://cloud.cerebras.ai/)
   (free tier available). `SERPER_API_KEY` is optional — `WebSearchTool`
   (Milestone 4) tries it first and falls back automatically to a keyless
   `ddgs`-based search if it's absent, invalid, or unauthorized (see
   Milestone 4's Part B above).

   Milestone 4's ONNX embedder (used for memory) downloads a small
   (~80MB) local model file on first use, cached under
   `~/.cache/chroma/onnx_models/` — the first run that touches memory
   will pause briefly for that download; every run after is instant and
   fully offline.

4. **Run the pipeline** (from the `deal_room/` directory):

   ```bash
   PYTHONPATH=src python -m deal_room.main
   ```

   As of Milestone 4, this runs the hierarchical crew **twice** in the
   same process: once against a hardcoded fictional startup pitch, then
   again on a follow-up question about the same company that doesn't
   re-supply its figures — checking whether CrewAI's memory recalls them
   (see Milestone 4's Part A above for why that second call's result
   isn't guaranteed and needs to be read from the actual output, not
   assumed). Each `Task` still prints the final `InvestmentMemo` plus
   execution stats (wall-clock time, token usage, and memory's own
   separately-tracked LLM usage) — to see *how* the Managing Partner got
   there (which specialists it consulted, in what order, any re-queries,
   any tool calls), pipe stdout to a log file, since delegation and tool
   calls only show up in the verbose trace:

   ```bash
   PYTHONPATH=src python -m deal_room.main 2>&1 | tee /tmp/m4_run.log
   ```

   For the delegation-behavior verification (normal pitch vs. a
   deliberately vague-financials pitch, run back to back with separate
   logs), run:

   ```bash
   PYTHONPATH=src python -m deal_room.test_hierarchical
   ```

   For the Milestone 4 integration test (memory + both tools together,
   confirming tool invocation via CrewAI's event bus and reporting cost
   vs. the M3 baseline — see Milestone 4's Part C above), run:

   ```bash
   PYTHONPATH=src python -m deal_room.verify_m4_integration
   ```

   To (re)generate the sample pitch deck PDF used by `PitchDeckReaderTool`
   (already committed at `src/deal_room/sample_data/brightledger_pitch_deck.pdf`,
   regenerating just overwrites it with the same fictional content):

   ```bash
   PYTHONPATH=src python -m deal_room.generate_sample_pitch_deck
   ```

## Troubleshooting

**`litellm.BadRequestError: LLM Provider NOT provided. Pass in the LLM
provider you are trying to call.`**

This means the model string lost its `cerebras/` prefix somewhere before
reaching LiteLLM — a known issue class with several of CrewAI's non-native
providers (it's been reported with Gemini too). Check that:

- The `LLM` object in `crew.py` still has `model="cerebras/..."` (not just
  `"gpt-oss-120b"`).
- That `LLM` instance is passed directly to the `Agent` via `llm=`, not
  inferred from an `OPENAI_MODEL_NAME` env var — that variable only works
  for OpenAI-shaped defaults.
- You haven't set `OPENAI_MODEL_NAME` anywhere in your shell environment
  that could shadow the explicit LLM object.

**CrewAI demands `OPENAI_API_KEY` even though you're not using OpenAI**

With an explicit `LLM` object this shouldn't happen, but if some internal
validation still complains, set a dummy value rather than a real OpenAI
key:

```
OPENAI_API_KEY=NA
```

This is a documented CrewAI quirk, not a real dependency on OpenAI.

**`ValidationError: manager_agent_in_agents`**

The Managing Partner (or whichever agent you're using as `manager_agent`)
showed up in the crew's `agents` list too. In this codebase that happens
if `managing_partner()` in `crew.py` gets decorated with `@agent` — that
decorator auto-registers the method into `self.agents` regardless of
whether any task references it. Keep it a plain, undecorated method,
called only once when building the `Crew`.

**"Manager agent should not have tools" exception**

If you pass `tools=` to the Managing Partner's `Agent(...)` construction,
`_create_manager_agent` raises rather than silently stripping them —
CrewAI reserves the manager's tool slots for its own delegation tools.
Don't give the manager agent explicit tools in a hierarchical crew.

**`Error executing tool. coworker mentioned not found`**

Seen once in testing (see README's Milestone 3 verification section) — the
manager's tool call didn't include a `coworker` argument matching one of
the crew's agent roles closely enough. CrewAI's coworker matching is
whitespace/case-insensitive and usually self-corrects on the next tool
call, but if it happens repeatedly, check that agent `role:` strings in
`agents.yaml` don't contain anything unusual (extra punctuation, etc.)
beyond the normal YAML folding.

**`LLMContextLengthExceededError` / `429 Tokens per minute limit exceeded`**

A real Cerebras rate limit, not a code bug — CrewAI's error message is
misleading (it's phrased as a context-length problem; the underlying cause
is `429 too_many_tokens_error`). Enabling memory (Milestone 4) makes this
much more likely: every agent step adds its own save/recall LLM call on
top of the crew's own calls (see Milestone 4's Part A — 75 memory-related
requests were observed in a single run, more than the crew's own 22).
`crew.py`'s `kickoff_with_retry()` retries with a cooldown
(`RATE_LIMIT_COOLDOWN_SECONDS`) for exactly this case.

**`429 Tokens per day limit exceeded`**

A different, harder failure than the per-minute one above — this is a
daily quota, so retrying with a short cooldown won't help; the error
recurs identically until the quota actually resets. Confirmed in testing
that this quota is shared at the **Cerebras account level, not per API
key** — swapping in a second key from the same account hit the identical
error on the very first LLM call of the next run. If you hit this, either
wait for the account's daily quota to reset, or use a key from a genuinely
different account.

**`Invalid type Memory for attribute 'crew_memory' value. Expected one of
['bool', 'str', 'bytes', 'int', 'float']...`**

A harmless warning seen in verbose output once Milestone 4's memory is
enabled — some internal tracing/telemetry serialization step tries to log
the crew's `memory` field and can't represent a `Memory` object as one of
its primitive-typed fields. Cosmetic; doesn't affect memory's actual
save/recall behavior.

## Milestone roadmap

- **Milestone 1** ✅: single agent, single task, structured
  `output_pydantic` result, Cerebras via LiteLLM.
- **Milestone 2** ✅: sequential crew with 4 independent specialist
  analysts (financial, market, technical, risk) plus a synthesis task that
  combines their structured output into a single `InvestmentMemo` via
  `context` chaining — no re-reading of the raw pitch by the synthesis
  agent.
- **Milestone 3** ✅: hierarchical crew (`Process.hierarchical`) — the
  Managing Partner becomes the crew's `manager_agent` and dynamically
  delegates to the 4 specialists via a single open-ended task, rather than
  running a fixed final task over pre-computed outputs.
- **Milestone 4** ✅ (this one, partially verified live — see its section
  above): CrewAI unified memory (local ONNX embeddings + a dedicated
  Cerebras analysis LLM, no OpenAI dependency) plus two custom tools
  (`WebSearchTool`, `PitchDeckReaderTool`). Tools are fully verified live
  with real invocation counts and evidence in the final output. Memory's
  mechanism is verified in isolation; the full two-kickoff recall claim
  and the dedicated integration script are written and ready but blocked
  on a real Cerebras account-level daily quota exhaustion, not a defect.
- **Milestone 5**: wrap the crew in a CrewAI `Flow` for more control over
  branching, state, and multi-step orchestration beyond a single
  `kickoff()` call.
